How each level works

Understanding DVWA Security Levels

Level What DVWA usually changes What to look for Defensive lesson
Low Little or no filtering User input appears in the page unsafely Untrusted input must never be inserted into HTML without encoding
Medium Partial filtering or weak blacklist checks Simple tags or patterns may be altered, but context is still unsafe Blacklists are unreliable and easy to bypass conceptually
High Stronger filtering or encoding attempts Some vectors fail because of better escaping Correct context-aware output encoding is the real control
Impossible Proper escaping/sanitization and safer handling Input should render as text, not executable code This is the target design you should aim for
🪞

Reflected XSS

Immediate reflection without encoding

Reflected XSS happens when the page takes input from the request and immediately echoes it back into the response without safe output encoding. In DVWA, the lesson is that the application should treat the input as data, not HTML or script.

  • 1 Identify the input source, usually a form field or URL parameter.
  • 2 Check whether the input is reflected back into the page.
  • 3 If the output is not encoded, the browser may interpret it as executable content.
  • 4 The correct fix is context-aware escaping before rendering, especially HTML entity encoding in page content and proper encoding for attribute or script contexts.
  • 5 A safe validation step is to enter harmless text and confirm how it is displayed, then document whether the application encodes special characters or not.
💾

Stored XSS

Unsafe persistence

Stored XSS happens when the application saves untrusted input in a database or other storage and later displays it to users without proper escaping. The key idea is persistence: once the value is stored, every future page view can be affected.

  • 1 Find a field that saves content, such as a guestbook or comment form.
  • 2 Submit a normal test string first and see whether it appears later exactly as entered.
  • 3 If the page later displays stored content without encoding, that is the weakness.
  • 4 The fix is to sanitize only if rich text is required, but most importantly to escape output when rendering stored data back into HTML.
  • 5 Use safe rendering rules everywhere the stored value is displayed, not just at the time of input.
🌐

DOM XSS

Unsafe client-side manipulation

DOM XSS happens entirely inside the browser. The server never sees the attack! It happens when the website's JavaScript takes your text and blindly runs it.

  • 1 Check if the website's code reads from the URL (like a parameter `?name=...` or a hash `#...`).
  • 2 See if the code takes that text and passes it to a dangerous tool like innerHTML.
  • 3 Why is innerHTML bad? Imagine innerHTML is a very gullible robot. If you hand it a piece of paper that says "Build a bomb", it will actually try to build the bomb! It executes whatever code you give it.
  • 4 The Fix: Use textContent! Imagine textContent is a smart, safe robot. If you hand it the same paper that says "Build a bomb", it just tapes the paper to the wall. It refuses to execute the instructions; it just displays them safely as text.
  • 5 To defend against DOM XSS, always use safe tools like textContent or innerText instead of innerHTML.

Manual Exploitation Methods

Step-by-step payloads for all DVWA levels

Here are practical manual methods to solve the DVWA XSS challenges at various security levels.

Reflected XSS

  • Low No filtering. Payload: <script>alert(1)</script>
  • Med Strips lowercase <script> tags. Bypass using mixed case: <SCRIPT>alert(1)</SCRIPT> or nested tags: <scr<script>ipt>alert(1)</script>
  • High Strict regex filtering of script tags. Bypass by using event handlers on other elements: <img src=x onerror=alert(1)>
  • Imp Impossible: The server uses a translator (htmlspecialchars) to turn dangerous brackets into safe HTML entities (like &lt;). The payload just renders as boring text!

Stored XSS

  • Low Submit <script>alert(1)</script> in the "Message" field.
  • Med The Message field filters tags, but the Name field does not. However, the Name field has a max-length in the HTML. Use DevTools to change maxlength="10" to "100", then submit the payload in the Name field.
  • High Similar to Medium, use DevTools to expand the Name field limit and inject a non-script payload: <img src=x onerror=alert(1)>.
  • Imp Impossible: Just like Reflected XSS, the server uses the htmlspecialchars translator on BOTH the Name and Message fields before storing/rendering them. The magic is completely broken before it even reaches the database.

DOM XSS

  • Low Append payload to URL parameter: ?default=<script>alert(1)</script>
  • Med Closes the select dropdown before injecting: ?default=</option></select><img src=x onerror=alert(1)>
  • High Server enforces strict allowed words ("English", "French"). Bypass using the URL hash fragment (#) since it's never sent to the server: ?default=English#<script>alert(1)</script>
  • Imp Impossible: The JavaScript uses the safe, smart robot textContent instead of the dangerous, gullible robot innerHTML. It safely displays the text without executing it!

Automated Testing Methods

Tools to find XSS faster

While manual testing is crucial for understanding, real-world bug bounty hunting and pentesting rely on automated tools to scale up the search.

  • 1 Burp Suite (Intruder)
    Intercept the request in Burp Suite, send it to Intruder. Highlight the input parameter (e.g., name=§test§) and load a payload list (like SecLists XSS polyglots). Start the attack and sort the results by length or use Burp's "Grep - Match" feature to see which payloads successfully reflected back safely in the response HTML without being sanitized.
  • 2 XSStrike
    XSStrike is a powerful XSS detection suite. Instead of just injecting a giant list of payloads, it analyzes the context and dynamically generates custom payloads that bypass filters.

    Run the command in your terminal (remember to grab your DVWA session cookie):
    python3 xsstrike.py -u "http://[IP]:[PORT]/vulnerabilities/xss_r/?name=test" --headers "Cookie: security=low; PHPSESSID=your_id"
  • 3 OWASP ZAP (Zed Attack Proxy)
    Use the Active Scan feature. Right-click the vulnerable DVWA node in the Sites tree and select "Attack > Active Scan". ZAP will automatically fuzz all input fields and URL parameters with XSS vectors and alert you if it detects a successful execution sink.
🛠️

Fixes to include

  • ✓ Context-aware output encoding for HTML, attributes, URLs, and JavaScript contexts.
  • ✓ Input validation to reject obviously invalid data, but not as the only defense.
  • ✓ HTML sanitization only when rich text is truly required.
  • ✓ Safe DOM APIs such as textContent and innerText instead of innerHTML.
  • ✓ Content Security Policy as an additional layer, not a primary fix.
🏁

Conclusion

“DVWA shows that XSS is not just about user input, but about how the application processes and outputs that input. The secure design is to encode output correctly, avoid dangerous JavaScript sinks, and never trust browser or server input by default.”

“DVWA demonstrates how XSS arises when untrusted input is inserted into a page without correct context-aware escaping. Low security shows the flaw directly, medium and high show partial filtering, and impossible represents secure handling. Reflected XSS affects immediate responses, stored XSS persists in server data, and DOM XSS occurs in client-side code. The correct defense is context-aware output encoding, safe DOM methods, and sanitization only where HTML is intentionally allowed.”
